1. Mini App: Test I/O at large scale

This mini-app tests large-scale I/O for Feel++. The I/O operations measured here are representative of those performed in the demonstrators, where mesh loading and field export can become performance bottlenecks for large-scale simulations.

1.1. Description of the benchmark

This mini-app repeats the following steps a given number of times:

  • Load a mesh \(\mathcal{M}\) with discretization size \(h\)

  • Create a function space \(X_h = P_{c,h}^d\) for the desired discretization order \(d\)

  • Create a vector-valued function space \( \mathbf{X}_h = ( P_{c,h}^d )^3 \)

  • Create a vector \(u \in X_h\) and export it to disk

  • Create a vector \(\mathbf{u} \in \mathbf{X}_h\) and export it to disk

  • Write the loaded mesh to disk

Exports are performed in two ways: (i) write at format HDF5 on the disk directly, (ii) use the exporter functionality of Feel++. For the second, we provide more details. The two fields are interpolated to a \(\mathbb{P}_1\) field before being saved on the disk. The mesh is also exported in this process. The time measured is the time to perform projections of \(u\) and \(\mathbf{u}\) and to save the files.

This whole process is iterated a given number of times.

1.3. Benchmarking Tools Used

This benchmark was performed on the gaya supercomputer, using feelpp.benchmaring (v.{feelpp_benchmarking_version}). The performance tools integrated into the Feel++-toolboxes framework were used to measure the execution time.

This mini app can be run with any mesh family. The results presented in this document are obtained with a 3D mesh of a realistic geometry of a human eyeball (Saigre, Prud’Homme, & Szopos, 2024), with various level of refinement. The steps to obtain this mesh, stemming from a human eyeball CAD are presented in (Chabannes et al., 2024). The figure below presents the mesh, and the level disparity of the refinement according to the region considered.

Figure 1. Mesh discretization, with the various regions of the eye.

1.4.2. Output Data

The monitored quantities are the average times for each of the steps run in the loop described above: (i) time_loadMesh, the time taken by the application to load the mesh from the disk; (ii) time_createFunctionSpace, the time taken to create the functional space \(X_h\) or order \(d\); (iii) time_saveMesh, the time taken to write the mesh data on the disk, in a new file; (iv) time_export, the time to export the vector \(u \in X_h\) to disk, using the exporter functionality of Feel++. The times are stored in a JSON file during execution.

1.5. Results summary

We present in the figures below results over the mesh family for various numbers of parallel tasks. The mini-app is run on the cluster gaya. The results presented are obtained with the degree of discretization \(\mathbb{P}_1\). Similar behavior is observed for other discretization orders.

Note that some points are missing, either because the memory required exceeded what was available on a compute node, or because the iterative process took longer than the job timeout.

We see that mesh reading and function-space creation scale well with the number of parallel processes with a limit reached at np = 96 for the small meshes.

Conversely, the steps writing data to disk do not scale with more parallel processes. Times increase or stagnate This loss of performance stems from coordination among parallel processes when writing to a single destination. Because the mesh is pre-partitioned, the reading step does not suffer the same issue.
